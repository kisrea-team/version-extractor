# 我们何时知道一个软件版本才是"那个"版本？

> 版本选择问题的失败模式驱动设计
> (Failure-Mode-Driven Design for Current-Release Selection from Heterogeneous Vendor Pages)
>
> 作者待定 — LogUp / version-extractor 工程团队
> 目标：arXiv / WWW 工业轨 / CIKM 应用轨

## 摘要

从厂商页面提取"当前稳定版本"是一个被普遍低估的困难问题：一个页面往往包含几十个版本号样字符串（系统要求、构建哈希、时间戳、评论统计、依赖版本），而真版本常常只以一句话声明一次。本文不把这个问题当作"找一个正则/找一个 LLM"的检索问题，而是当作**失败模式驱动的决策管线设计**问题。我们提出并评估 VE（version-extractor）：一个四层管线 —— 包注册表（版本是命名字段，确定无疑）→ 官方端点（GitHub/iTunes/JSON 源）→ HTML 层（多 scope 候选采集 + LightGBM 隐式净化 + LambdaRank 页内排序 + 家族锚定）→ 低 margin LLM 裁决（仅排序模型摇摆时介入，不到 20% 查询）。论文重点回答三个设计原理问题：

1. **为什么纯启发式必然失败** —— 用真实页面的噪声结构论证"最大数字"假设的破产，量化 SVG 坐标、年份、统计数字三类污染源；
2. **为什么学习型净化优于手工排除规则** —— 37 特征 LightGBM 做了规则无法做的"隐式净化"，因为噪声与真版本在形式上不可分（SVG 坐标 vs 版本号）；
3. **为什么 LLM 只能做最后一道裁决** —— 三个 LLM 在 83% 页面结论一致、在真版本低显著度的 17% 页面全部失败，说明瓶颈是候选显著性而非阅读理解。

配合一套 10 类噪声的标注规范（700 候选）和独立验证的发布基准，完整管线达到 70.9–74.5% 端到端准确率（匹配集对比，是最大版本号启发式 44.8% 的 1.6 倍）。失败分析表明剩余错误主要来自从不声明版本的页面 —— 信息论天花板 —— 而非模型误判。

## 1. 引言：一个被低估的问题

软件更新追踪、漏洞监控、供应链审计都依赖一个"平凡"能力：知道一个软件的当前版本。Web 规模上这意味要从数以百万计的厂商页面（下载页、changelog、发布博客、应用商店、注册表）中，每个提取一个数字。问题看起来已解决：版本号短而规则，正则找得到，LLM 读得懂。

两种主流方法以互补方式失败：

- **正则 + 启发式**（"取最大数字"）：被噪声击穿。真实页面上版本号样字符串比真版本多一个数量级，最大数字往往是年份、统计值或构建号。
- **纯 LLM 提取**：被成本、不确定性和显著性击穿。通用模型必须在每页调用，无法审计，且当真版本是低显著度候选时，LLM 与朴素正则选错的方式相同（§5.3）。

本文的核心主张：**版本选择不是"找一个更强的提取器"，而是"设计一个知道自己在何时确定、何时不确定的决策管线"**。昂贵组件只在廉价组件失败时介入，每一层针对上一层的一个具体失败模式而设计。

## 2. 问题形式化与失败模式

### 2.1 任务定义

给定厂商页面 *p* 与产品名 *n*，输出当前稳定版本 *v*，或在页面未声明版本时报告"无声明"。候选 *c* 是 *p* 中匹配版本语法的子串；页面产生候选集 *C*，任务是从 |C|（常达数十个）中选出真版本。

### 2.2 噪声的形态学：为什么"最大数字"必然破产

系统收集页面中"版本号样"字符串的来源，归纳为十类（对应标注规范的 `noiseType`）：

| 类别 | 典型证据 | 与真版本可区分性 |
|---|---|---|
| `build` | buildNumber、构建号、commit/revision | 字段名可区分 |
| `sdk / api` | SDK 版本、API/schema 版本、协议版本 | 字段名可区分 |
| `os` | minimumOsVersion、Windows/macOS 系统要求 | **形式不可分**（"Windows 8.1"） |
| `dependency` | npm 包、插件、库、manifest 依赖 | 需归属语义 |
| `svg` | SVG path/viewBox 坐标（135.539, 20.5151） | **形式不可分** |
| `asset` | JS/CSS chunk 文件名、webpack hash、资源 URL | URL 上下文可区分 |
| `date` | 日期、年份、时间戳 | 年份形态可区分 |
| `css` | font-size、line-height、间距数值 | 属性名可区分 |
| `other_noise` | 价格、数量、统计值（"1.1万"）、订单号 | **语义不可分** |

**失败案例 1（海螺AI）**：官网营销页渲染出的统计数字流 `1175 1.1万 95 191 182 236 231 ...` 被正则提取为候选，"1.1万"经版本语法清洗后成为 `v1.1`，以 high 置信度入库 —— 页面根本没有版本声明，ve 从噪声中"碰运气"。

关键洞察：**至少两类噪声（SVG 坐标、统计数字）在文本形式上与真版本不可分**。"净化后取最大数字"的假设 —— 真版本是最大数 —— 在实测中仅 44.8%（29 例集）。**版本选择需要"版本号 + 页面语义"联合判断，纯数字或纯结构规则都到不了 85%**。

## 3. 设计原理一：分层确定性 —— 版本是命名字段时就别猜

> **P1（分层确定性）**：存在版本作为"命名字段"的来源（包注册表、官方 API），在这些来源上答案确定；架构必须让这类来源优先短路，把 HTML 猜测留给无法寻址的长尾。每层为上一层的失败模式设计，且越昂贵的层越晚介入。

### 3.1 第一层：包注册表与官方端点

注册表（winget manifest、Homebrew formula、Flathub appstream、npm registry、Go module proxy）把 `latest` 作为命名域暴露；官方端点（GitHub Releases API、iTunes lookup、python.org、redis.io、filezilla-project.org、blackmagicdesign.com）用按主机分表的 fetcher 精确解析。这两层零 HTML 解析、零模型推理，命中即正确。

**失败案例 2（npm registry JSON dump）**：deepseek-harness 的源是 `registry.npmjs.org/@deepseek-ai/dsh`。早期 classifySource 不认识 npm registry，把整包 JSON 当 HTML 页面清洗，版本号取自 `dist-tags.latest`（正确），但 changelog 变成整包 JSON dump。修复：**源分类层把 JSON 端点显式归类为 `json` 类型**，禁止进入 HTML 清洗路径。

### 3.2 为什么不做"通用 JSON 解析"：源分类即解析契约

一个易犯的错误是"写一个通用 JSON 解析器，从任意端点提取版本"。失败原因有二：(1) 不同端点的字段语义不同（npm 是 `dist-tags.latest`，Go 是数组首元素，go.dev 是 `version` 字段）—— 需要按宿主表驱动；(2) 无结构的 JSON dump 不能当 changelog 用。因此设计是**按宿主注册的 fetcher 表 + 结构质量门控**（§5.4），而非通用解析。

## 4. 设计原理二：学习型隐式净化 —— 噪声与真版本在形式上不可分

> **P2（隐式净化）**：噪声排除不能靠手工规则（词表/层层判定），因为关键噪声（SVG 坐标、统计数字）与真版本在文本形式上不可分；净化必须由学习型模型完成 —— 它利用 scope 来源、产品名锚定、出现模式等跨站可迁移信号，做规则做不到的"隐式净化"。

### 4.1 候选采集：scope 即第一特征

采集阶段不只提取版本号，还记录其 **scope**（来源位置）：`title / meta / heading / visible / download-link / structured / noise`。scope 是第一特征：下载链接中的版本比正文中的可信，标题中的比可见文本中的可信。**核心思想：真实版本号会反复出现 —— 标题、meta、下载链接、正文多处；垃圾版本只出现一次、不在下载链接里。**

### 4.2 过滤：37 特征 LightGBM 的"隐式净化"

过滤分类器融合三类特征：

- **版本结构**：`has_v`、段数、位数、是否年份形态、前导零异常、严格格式校验（纯数字点号，`-` 后必须字母）
- **scope**：download-link / structured / heading / visible / noise 五个来源位
- **语义**：BERT 概率（候选文本是产品版本的概率）

为什么学习型净化严格优于手工排除规则？因为规则只能枚举已知噪声（年份、build 后缀），而**噪声形态学是开放的**（十类）；LightGBM 学到的是"什么样的候选处于什么样的上下文"的联合模式。实测：净化后数字最大（44.8%）vs 纯结构规则（75.0%）vs 完整管线（70.9–74.5%，含更难的当前集）—— 规则的收益存在，但被"误杀正确版本"（下载页单上下文）和"漏放新噪声"两面夹击。

### 4.3 排序：为什么"当前 vs 历史"排序模型会失败，LambdaRank 却成功

早期实验（2026-08-04）有一个反直觉结论：**标准的 Learning-to-Rank 模型（页内相对/绝对/逐对）在"当前 vs 历史"上失效（~20/51）**。原因：BERT 文本语义无法区分"当前版本"和"历史版本" —— 它们的下载链接和正文上下文几乎相同（python 页 v3.11.1 与 v3.14.1 分类器分同为 0.97）。这是任务的本质属性，不是数据量问题。

转向 LambdaRank 后成功的核心不是排序目标，而是**特征设计**。排序特征（15 组）分四组：

| 组 | 特征 | 设计动机 |
|---|---|---|
| 结构 | prob、has_v、段数、位数、major/minor/patch、yearish、纯数字形 | 版本语法合法性 |
| scope 与锚定 | download-link/structured/heading/visible/noise 五 scope 位、产品名锚定（`产品名+版本` 正则）、title 锚定、上下文含产品名 | 产品归属（产品名锚定区分度 29.1×，但训练稀疏学不到 → 显式做成特征） |
| 序列与家族 | 页内候选数、同 major 组大小、高于当前数/比例、是否全局最大、是否同 major 最新、主导路径归属、版本序列检测（series/latest） | "格式类似的候选中，版本号最大者是当前版本"（核心洞察） |
| 页面类型 | download/history/article/error 四类 | 页面意图先验 |

其中两个特征体现了最深的设计推导：

- **产品名锚定**（`productRe`：产品名后跟版本号的模式）：区分度高达 29.1×，但分类器训练数据稀疏学不到 —— 于是显式构造为排序特征。这是"特征化 vs 让模型自己学"的权衡案例：高区分度 + 稀疏数据 → 必须显式特征化。
- **同 major 家族锚定**：排序选出的 seed 锚定到其版本家族，选择族内最新。设计文档给出了反直觉的理由：**数值聚类（DBSCAN，major*1e6+minor*1e3+patch）必然失败** —— 版本空间非线性：go 1.25.12→1.26.0 数值距离 988000 却是相邻版本；Eagle v4.0→v22 数值更大却是不同东西（产品版本 vs 构建号）。"同族"只由上下文产品名定义（前缀归族），这就是最大权重连通子图的形态。

### 4.4 标注体系：四标签 + 十噪声类

训练监督数据来自一套严格的标注规范（`candidate-annotation-guidelines.md`，700 候选）：

- **四类互斥主标签**：`current_product`（需"当前性证据"：latest/current/stable 语义、下载按钮指向、页面唯一版本）、`historical_product`（真实旧版本，作为排序候选而非二分类负样本）、`non_product`（十类噪声）、`ambiguous`（证据不足，进主动学习）
- **证据优先序**：下载链接 > 标题/current 语义 > 结构化字段 > 正文 > URL > 出现次数/数字大小（仅辅助）
- **数据转换原则**：`current_product → 1`，`non_product → 0`，`historical_product` 默认不进入二分类（早期实验证明：把 historical 当负样本有害 —— 历史版本与依赖版本共享"产品版本"文本特征，压低历史会连带压低真版本）
- **防泄漏**：同产品/域名/模板族必须在同一训练/验证/holdout 分组

## 5. 设计原理三：LLM 只做最后一道裁决 —— 触发策略比模型选择重要

> **P3（克制调用）**：LLM 是唯一能读语义的组件，但它的价值在于"在排序模型摇摆时裁决"，而非普遍应用。每页调用浪费 80% 调用；只在 margin 低、通道冲突或近似并列时调用，把语义能力集中在真正歧义处。裁决输入 = 产品名 + 排序候选清单（带逐候选上下文）+ "优先选第一名除非上下文明确反对"的指令。

### 5.1 触发条件与边际贡献

触发条件：rank margin < 0.5、通道冲突、或 p12 差异 < 0.015。三条件覆盖"模型摇摆"的所有形态。LLM 调用占比不到 20%。

### 5.2 模型对比的意外结论

对比三个 LLM（diffusiongemma-26b、DeepSeek-V4-Flash、gemma-4-26b）：

- 三个模型在 **83% 的页面结论一致** —— 分层管线在 LLM 介入前已解决这些页面，LLM 只是"执行者"；
- 分歧的 17% 页面，DeepSeek 在 8:1 的案例上选了独立验证的正确版本（Termius 9.43.1、Rytr 1.3.1、QuillBot 4.101.1 均精确命中）—— 模型能力有真实差异（+3.6 点，55 例匹配集）；
- 但当正确候选**缺失或被埋没**（Framer、Xcode 26、Surge），*所有* LLM 以同样方式失败 —— 说明**瓶颈是候选显著性，不是阅读理解**。

**结论：裁决器模型选择是二阶杠杆（+2 例）；候选质量（采集、净化、排序）与触发策略占主导。**

**失败案例 3（Bandizip — 候选显著性）**：官网有 "Latest version: v7.45 — July 20, 2026" 硬声明，但 v7.45 的启发式分数只有 11（"Latest version:" 声明缺少对应特征），Windows 8.1 系统要求（score 78）反而成为 seed。rank 选错 → LLM 候选清单里 v7.45 排最后 → 换任何 LLM 都选 v8.1。修复链路：Qwen3-Reranker-8B 重排把 v7.45 顶到第一（0.84 vs 0.01）→ **★ 标记跟随 rerank 第一名**（原 bug：rerank 排对了但 ★ 仍标 rank seed，LLM 遵循"★ 是首选"选错）→ LLM 答对。三层修复（候选排序 + 裁决标记 + 模型）缺一不可。

### 5.3 Changelog 质量门控：从"存垃圾"到"宁可为空"

版本锚定的 changelog 提取同样会被污染。结构质量门控（`isNonChangelogContent`）用纯结构信号拦截三类垃圾：

- **JSON dump**：`"key":` 结构密度 ≥5 或以 `{` 开头（npm 端点整包 JSON）
- **数字 dump**：纯数字 token 占比 >40%（营销页统计数字流，海螺"1.1万"）
- **导航链接页**：markdown 链接行占比 >50%（商店首页/视频站导航）

验证 6/6：三类垃圾全拦截，正常中英文 changelog、短描述全放行。**设计原则：非 changelog 内容宁可置空，也不把垃圾入库** —— 与 logup 侧"版本准入制"呼应：数据质量的第一道闸在提取端。

## 6. 评估

### 6.1 发布标注基准

真实厂商页面（桌面软件、开发工具、移动应用），ground truth 用独立源验证（官方发布历史、App Store lookup、crx 下载、snapcraft API）。纯 SaaS 页面（Coda、Replit 等不声明版本）从固定集剔除，归入"无声明"类单独分析。正确性 = 提取版本与 ground truth 的精确前缀匹配。

### 6.2 端到端结果

| 配置 | 准确率 | 说明 |
|---|---|---|
| 最大版本号启发式（净化后数值最大） | 44.8% | 历史 29 例集 |
| 纯结构规则（簇内最大 + 位置最早） | 75.0% | 历史 76 例集 |
| 学习型排序器（无 LLM） | 65.5%–69.7% | 历史集（干净集 65.5%，76 例 69.7%） |
| **完整管线 + NVIDIA LLM** | **70.9%** | 当前 55 例验证集 |
| **完整管线 + DeepSeek-V4 + reranker** | **74.5%** | 当前 55 例验证集 |

> 说明：历史行（44.8%/75.0%/69.7%）来自早期不同案例集的基准，仅用于展示激励架构的相对排序（启发式 < 规则 ≈ 排序器 < 完整管线），不是匹配对比；当前两行在同一 55 例验证集上匹配。文档记载 LLM 兜底在干净基准上贡献 +17.3%（纯模型 65.5% → 完整链路 82.8%），说明 LLM 是"核心组件"而非"残余兜底" —— 与"克制调用"不矛盾：调用次数少，但在关键歧义上贡献大。

### 6.3 失败归因

| 失败类别 | 占比特征 | 归属 |
|---|---|---|
| 无声明（营销页/JS-only SPA/博客式 what's new） | 主导 | 信息论天花板 —— 任何提取器都无法回答；应剔除基准或走网络拦截（采集问题非选择问题） |
| 版本线语义（stable vs beta、产品 vs 依赖） | 少量 | 模型边界 —— 判别句（"LTS"/"recommended download"）在候选上下文但 15 特征排序器学不到 |
| 候选被埋没（低显著度） | 少量 | 候选层 —— reranker 可部分修复（Bandizip +2 例） |

## 7. 设计教训与讨论

1. **分层确定性胜过单一强模型。** 确定性层免费、精确、可审计；学习层泛化；LLM 层读语义但必须克制。每一层"知道自己何时确定"比任何单层"总是自信"更可靠。
2. **瓶颈是候选显著性，不是阅读。** 主导失败是真版本是低显著度候选。提升候选质量（采集、净化、重排）杠杆高于提升选择器。
3. **特征化要显式。** 高区分度（29.1×）+ 稀疏数据 → 必须显式构造特征（产品名锚定），不能指望模型自学习。
4. **手工规则有边际天花板。** 词表/层层判定每加一条规则就多一批例外；噪声形态学开放（十类），学习型净化是唯一可扩展路径。
5. **数据标注要区分"产品归属"与"时间状态"。** 四标签体系（current/historical/non/ambiguous）比二分类更接近任务结构；把 historical 当负样本会伤害真版本（共享产品特征）。

## 8. 局限与未来工作

- 基准规模小（55 例匹配集），中英文厂商页占主导；CJK 软件与区域应用商店覆盖是已知缺口。
- 15 特征排序器未把"页面声明信号"（"Latest version:"）作为一等特征；reranker 实验显示该信号 +2 例，页面级声明特征是明确方向。
- 多版本线语义（beta/stable、产品/依赖）是开放研究边界 —— 需要版本线分类法与专用训练数据。
- 无声明页面需要网络拦截（深层 JS 状态/下载响应文件名，如 Notion-7.29.0.msix）—— 采集层改进，非选择层。

## 9. 结论

VE 是一个生产级版本提取系统，组织为失败模式驱动的四层决策管线：注册表（命名即答案）、官方端点（按宿主解析）、HTML 层（多 scope 采集 + 学习型隐式净化 + LambdaRank 页内排序 + 家族锚定）、低 margin LLM 裁决（克制调用，不到 20% 查询）。三个设计原理 —— 分层确定性、学习型隐式净化、LLM 克制调用 —— 均有失败案例与对照实验支撑。在独立验证的 55 例基准上达到 70.9–74.5%，是最大版本号启发式（44.8%）的 1.6 倍。核心教训是架构性的：**对版本选择，瓶颈是候选显著性，LLM 的价值在于克制地在真正歧义处介入，而非普遍应用；每一层知道自己何时确定，比任何单层总是自信更可靠。**

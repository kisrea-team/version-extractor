# 版本提取架构设计复盘（2026-08-13 修订）

> 本文档为早期设计提案（2026-08-04）的复盘修订。
> 原稿预判"纯确定性路线可覆盖主流软件 85-88%"，经 2026-08-13 系统性验证（收益临界研究）**证伪**：
> 纯规则/确定性路线的实际天花板远低于此，真实架构必须依赖机器学习排序 + LLM 语义兜底。

## 一、确定性路线的实测上限（证伪原预判）

原设计"全部规则化实现，AI 仅对残余长尾兜底"的预估 85-88%，与实测严重不符：

| 纯确定性/规则方案 | 实测成绩 | 结论 |
|---|---|---|
| 净化后数字最大（版本号比较） | 44.8%（29 例）/ 37.8%（74 例） | 页面假最大（年份/统计/参数）污染严重 |
| 纯结构规则（簇内最大 + 位置最早） | 75.0%（76 例） | 高于 rank 纯模型 69.7%，但低于完整链路 |
| 声明块提取（decl-only） | 65.8% | 误杀正确版本（下载页单上下文） |
| page-type 分流 | 下载页 50% / 历史页 17% | 不可行 |

**规律：版本选择需要"版本号 + 页面语义"联合判断，纯数字/纯结构规则都到不了 85%。**

## 二、真实架构（与设计稿的差异）

原稿"三档递进（L1 启发式 → L2 网络拦截 → L3 版本体系守卫）"的 L2/L3 设想**没有成为主路径**。真实架构是：

```
① 包注册表（winget/brew/flathub）        ← 命名字段，命中即确定性正确（最强确定性源，保留）
② GitHub API / 官方 RSS / JSON 端点      ← 权威
③ 页面 HTML（长尾）：
     正则收集候选（多 scope 上下文）
     → LightGBM 过滤（37 特征：scope/产品名锚点/序列/归族）
     → LambdaRank 页内排序选 seed
     → 同-major 归族确认版本线
     → LLM 语义兜底（margin<0.5 或通道冲突或 p12diff<0.015）
```

**关键认知（与设计稿相反）：**
1. **AI 不是"残余长尾兜底"，而是核心组件**——LLM 兜底在干净基准上贡献 **+17.3%**（纯模型 65.5% → 完整链路 82.8%）。去掉 LLM，任何规则/模型组合都到不了 85%。
2. **LightGBM 的 37 特征在做"隐式净化"**——它比任何手工排除规则（年份/统计/参数）都好，这就是数字最大规则（44.8%）远不如 rank 的原因。
3. **L2 网络拦截仍是收集层出路**（版本只在 JS 配置/接口里的页面，如 Zotero `standaloneVersions`），但它解决的是"版本可不可得"，不是"哪个版本是当前"——后者是语义判断，网络拦截给不了。

## 三、核心难点：版本线语义（规则化不动的部分）

多版本线案例（Node.js LTS 24 vs Latest 26、MKVToolNix 25.x vs 100.0、RoboForm 主程序 vs 浏览器扩展、Mumble stable vs macOS 特例）的判别信息（"Latest Release"/"LTS"/"recommended download"）**全部存在于候选上下文**，但：
- 特征化（产品名锚点 29.1x 区分度）→ importance 低，训练数据稀疏学不到
- 纯规则 → 词表/层层判定（每加一条规则就多一批例外）
- 只有 LLM 语义理解能读（MKVToolNix "Released v100.0" 被组合触发救回）

**结论：版本线语义是模型能力问题，不是规则能覆盖的。**

## 四、收益临界结论（2026-08-13）

页面级提取（HTML → 版本号）的信息上限已被本架构逼近。真实水平约 **86-89%**（"页面确实声明版本"的网站）：

- 剩余失败 = 页面不声明（信息论极限，营销页/JS-only 页，应剔除基准）+ LLM 对版本线语义的判断力边界（3 例左右）
- 进一步提升需动收集层（网络拦截/接口级）或换更强语义模型，均超出当前架构边际收益

## 五、保留的正确部分

设计稿中以下判断依然成立：
1. **注册表/官方 JSON 端点是最高确定性源**——命名字段，命中即正确，主流软件优先走。
2. **主下载按钮定位**（L2.3）对下载页有效（LibreOffice `download_buttons` class 直接测试救回）。
3. **深 JS 站版本在接口/运行时态**——由网络拦截/全局态解决，渲染 HTML 拿不到。
